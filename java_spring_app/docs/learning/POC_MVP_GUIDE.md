# POC/MVP 方針メモ

> **作成日**: 2026-02-14
> **目的**: 勉強会でAIから学んだPOC/MVPの考え方を整理した資料

---

## 用語

| 用語 | 定義 |
|------|------|
| **POC** (Proof of Concept) | 技術・方式の実現性を小さく確認する試作。品質は最小、利用者は開発チーム内想定 |
| **MVP** (Minimum Viable Product) | ユーザーに価値を届けて学習するための最小完成形。実ユーザー利用を前提に必要な品質・バリデーションを備える |

---

## 目的の違い

| | POC | MVP |
|--|-----|-----|
| **問い** | 「技術的にできるか」 | 「ユーザーに価値が届くか」 |
| **目的** | リスクと工数見積りの精度を上げる | 実使用から学んで方向性を決める |

---

## 完成度/品質

| | POC | MVP |
|--|-----|-----|
| **UI** | 簡素でOK | 本番想定の基本品質 |
| **エラーハンドリング** | 簡素でOK | ログイン・バリデーション・エラー表示を備える |
| **性能** | 目安確認程度 | 公開範囲の漏洩防止・最低限の品質を確保 |

---

## このプロジェクトでの適用例

### POC候補（短期スパイクで可）

- 公開範囲フィルタのSQL/キャッシュ挙動（PUBLIC/FOLLOWER/MUTUAL/PRIVATEのフィルタ性能と漏洩防止）
- Spring Securityの権限判定（ロール＋公開範囲をどう組み合わせるか）
- 画像アップロードの制限・ストレージ接続（サイズ/拡張子/スキャン有無）

### MVPスコープ（現状案）

- ログイン必須の会員制
- 霊園ページ作成・編集・閲覧（オーナーは単独）
- 思い出投稿（テキストのみ、公開範囲は会員内で判定）
- フォロー（片方向、承認なし）
- 問い合わせ送信（メール通知＋DB保存）
- 公開範囲の判定・漏洩防止を一貫させる

---

## 優先する判断

| 課題 | 決定方針 |
|------|----------|
| 公開範囲の非会員可否 | MVPでは「ログイン必須」で固定 |
| 画像をMVPに含めるか | 含めない（テキストのみ） |
| 共同管理者 | なし（単独オーナー） |
| フォロー承認制 | なし（片方向のみ） |

※ 決定したら `REQUIREMENTS_v0.1.md` と `ARCHITECTURE_ISSUES_v0.1.md` を更新

## POCの進め方（テンプレ）

1. **目的**: 何を証明するかを1文で明記
   - 例: 「公開範囲フィルタが100件/100msで動く」
2. **成功基準**: 定量的な閾値を設定
3. **スコープ外**: UI整備・例外共通化などは含めないと明記
4. **期間**: 1〜2日単位で締める
5. **成果物**: 簡易コード＋結果メモ＋次の意思決定案

---

## MVPの進め方（テンプレ）

1. コア体験に必要な機能だけを要件化し、他は「後続タスク」に送る
2. セキュリティ・公開範囲・認証周りは本番想定の最低限品質を確保
3. リリース後に計測する指標（利用数、投稿数、離脱ポイント）を決める
